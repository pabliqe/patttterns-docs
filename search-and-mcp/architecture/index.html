Implementations

Location Function Language

⚠️ Client tokenize and MCP tokenize must stay identical. They operate on the same index, so drift produces inconsistent results. When you change one, update the other.

Surface 1 — Site topbar search + SERP

Section titled “Surface 1 — Site topbar search + SERP”
  • Entry point: src/lib/search.ts → searchPatterns(query, options) via usePatternSearch
  • Index source: /search-index.json (fetched client-side, cached in memory)
  • Autocomplete: SearchBar searches as you type (300ms debounce). Header field off /search; in-page lg field on /search (header search hidden). Arrows highlight; Enter with no highlight (or See all) opens /search?q=.
  • SERP: Search results page — in-page SearchBar (query editor), active-filter tags, library masonry + PatternCard. /patterns stays the Notion collection.
  • Relevance scoring: weighted on normalized fields — exact title match (100 pts) › title prefix (50) › contains (25) › description (10) › tag match (30/15). Conjunctions and / & are stopwords. Token match is enough to keep a hit.
  • Token-split: yes (as of April 2026)
  • Normalization: normalizeSearchText() / tokenizeSearchQuery() in src/lib/search-match.mjs (must stay in sync with MCP normalize() + tokenize)
  • Product spec: Search Results Page PRD · ROADMAP SEARCH

Tools

Section titled “Tools”
Tool Description
search_patterns Full-text search. Args: query (required), limit (default 10, max 50). Returns pattern_id, catalog_number, tags, hasGeneratedComponent.
list_categories All categories with URL and pattern count
get_pattern Single pattern by slug (e.g. /ux-patterns/drag-and-drop)

Search logic

Section titled “Search logic”
  • normalize(query) applied to the query
  • Token-split: all tokens must match at least one of searchText, title, description, or (for component search) tags
  • No relevance scoring — order follows index order (Notion source order); search_components prefers hits with code
  • Results capped at limit (hard max 50)
  • Component TSX is fetched from the Components API (op=active / op=code); MCP never mutates the artifact

Usage visibility

Section titled “Usage visibility”

Each MCP initialize / tools/call records a structured [mcp-usage] edge log (Netlify → Edge Functions logs) and increments a monthly Blobs counter via mcp-usage-log:

Field Where Notes
tool, status, duration_ms logs + Blobs e.g. get_component / ok / version_not_found
pattern_id, catalog_number, version_id logs + Blobs component fetches
component_bytes logs + Blobs size only — never TSX body
ip Netlify logs only short retention; ops anomaly review
ip_hash Blobs monthly stable anonymized client key
agent_hint, user_agent logs + Blobs soft identity (Cursor/Claude/…); spoofable
country, request_id logs (+ country in persist) Netlify context.geo / requestId

Blob store: patttterns-mcp-usage → key monthly/YYYY-MM.json (browse in Netlify Blobs UI).

v1 is visibility only — no rate limits.

Environment variables

Section titled “Environment variables”
Variable Required Effect
GEMINI_API_KEY No Enables AI answers in the proxy. Without it, proxy returns MCP results only.
ENABLE_AI_CHAT No Must be "true" to activate AI path. Any other value → MCP-only.

Both must be set in Netlify environment variables for full AI mode. The chatbot widget on docs.patttterns.com requires no environment variables — it calls the production proxy directly.
