PRD: Dynamic Soft Login for PATTTTERNS (Stack-Aligned)

1. Executive Summary

Section titled “1. Executive Summary”

Goal: increase authenticated conversion without hurting browsing flow by introducing optional, dismissible login prompts while preserving an optional hard login gate for guest bookmark saves.

Business targets:

  • Primary: move Social Login Rate from <2% toward 15%.
  • Secondary: improve Week 1 retention toward 5% by increasing saved-library ownership.

2. Current Stack Reality (What This PRD Must Align With)

Section titled “2. Current Stack Reality (What This PRD Must Align With)”

This repo currently uses:

  • Next.js App Router (Next 16) + React 19 client components.
  • Custom Supabase auth client (not NextAuth runtime flow for modal gate).
  • Global login modal store via Zustand (useAuthModal) and modal component LoginModal.
  • Optional hard anonymous save gate in bookmark flow using NEXT_PUBLIC_HARD_LOGIN_BOOKMARK_THRESHOLD.
  • Existing deferred save recovery via localStorage keys consumed by useUserSync after OAuth callback.
  • Existing analytics naming with image_clicked and save_pattern* events.

Implication: implement by extending existing auth-gate primitives, not by creating a parallel auth system.

3. Scope and Non-Goals

Section titled “3. Scope and Non-Goals”

In scope:

  • Optional dismissible soft login triggers for image zoom and component preview.
  • Soft prompts never block or defer the requested discovery action.
  • Keep hard gate behavior for bookmarks and make threshold configurable.
  • Keep chatbot and component usage counters cumulative; unset thresholds do not add product limits.

Out of scope:

  • Replacing auth provider or auth architecture.
  • Full growth experimentation platform.
  • Redesigning the entire modal visual language.

4. Prioritized Phases by Criticality

Section titled “4. Prioritized Phases by Criticality”

Phase P0 - Safety, Contracts, and Observability (Critical)

Section titled “Phase P0 - Safety, Contracts, and Observability (Critical)”

Objective: prevent regressions before feature rollout.

Deliverables:

  • Define canonical event taxonomy and thresholds used by code and analytics:
    • soft trigger event source: image_clicked.
    • hard trigger event source: bookmark save attempts (save_pattern*).
  • Introduce domain-specific env-driven config with no implicit thresholds:
    • NEXT_PUBLIC_SOFT_LOGIN_IMAGE_THRESHOLD.
    • NEXT_PUBLIC_SOFT_LOGIN_PREVIEW_THRESHOLD.
    • NEXT_PUBLIC_SOFT_LOGIN_EXPORT_THRESHOLD.
    • NEXT_PUBLIC_HARD_LOGIN_BOOKMARK_THRESHOLD.
  • Keep counters cumulative without a period reset.
  • Add tracking specs for:
    • login_modal_showed with mode: soft|hard.

Exit criteria:

  • Config contract documented; unset or false disables the corresponding gate.
  • No mismatch between product copy, event names, and code-level constants.

Phase P1 - Core Interceptor Logic (Critical)

Section titled “Phase P1 - Core Interceptor Logic (Critical)”

Objective: introduce soft interruption logic without breaking hard gate.

Deliverables:

  • Create a reusable client hook/service (for example useAuthInterceptor) that:
    • records image zoom, component preview, and code action counts.
    • evaluates optional thresholds using env config.
    • opens a soft modal without blocking the action.
  • Keep hard gate behavior for save action:
    • block a save that would exceed the configured guest threshold.
    • preserve current pending bookmark/save-all behavior.
  • Ensure deep-link context is preserved for image intent (hash/query/path).

Exit criteria:

  • Anonymous users see a soft modal only at/after a configured threshold.
  • Save hard gate remains in effect only when a threshold is configured.

Phase P2 - Modal Behavior Adaptation (High)

Section titled “Phase P2 - Modal Behavior Adaptation (High)”

Objective: support two modes in one modal primitive.

Deliverables:

  • Keep using the existing LoginModal and distinguish modes in login_modal_showed metadata.
  • Soft prompts are dismissible and never prevent the requested discovery/export action.
  • Preserve existing OAuth callback behavior and pending-bookmark recovery.

Exit criteria:

  • Mode-specific accessibility and interaction behavior verified.
  • No regression in existing manual/login-limit triggers.

Phase P3 - Cumulative Usage and UX Integrity (High)

Section titled “Phase P3 - Cumulative Usage and UX Integrity (High)”

Objective: keep counters and server decisions consistent without resetting product usage.

Deliverables:

  • Keep client soft-prompt counters cumulative across sign-in.
  • Keep chatbot quota authoritative on the server and ignore the old browser-only quota marker.
  • Keep authenticated chatbot access unlimited; do not clear the guest counter on sign-in.
  • Leave paid export enforcement blocked until a real server-side entitlement integration exists.

Exit criteria:

  • Soft prompts do not interrupt image zoom, component preview, or code actions.
  • Missing/false thresholds never become hidden product caps.

Phase P4 - Progressive Rollout and Tuning (Medium)

Section titled “Phase P4 - Progressive Rollout and Tuning (Medium)”

Objective: reduce risk while tuning conversion.

Deliverables:

  • Roll out behind env/config flag.
  • Weekly threshold tuning based on funnel metrics:
    • image/preview/export interactions -> modal shown -> sign-in started -> sign-in completed.
  • Document rollback procedure (disable soft gate quickly via env).

Exit criteria:

  • Stable conversion uplift with no significant drop in engagement metrics.

5. Validation Coverage

Section titled “5. Validation Coverage”

Use the existing Node test files and targeted lint/type checks for the current implementation.

A. Unit Coverage

Section titled “A. Unit Coverage”
  1. Access threshold logic
  • Counters increment without resetting after sign-in.
  • Missing/false thresholds do not prompt or cap usage.
  • Soft modal is shown once at/after the configured threshold and does not block the action.
  1. Server quota config
  • Missing/false values disable the corresponding limit.
  • Invalid values fail explicitly rather than becoming hardcoded caps.
  • Guest quota cookies have no usage reset period.

B. Manual Component Checks

Section titled “B. Manual Component Checks”
  • Soft prompts remain dismissible in image and component flows.
  • login_modal_showed includes mode: soft|hard.

C. Browser Scenarios

Section titled “C. Browser Scenarios”
  1. Anonymous image flow
  • After N image clicks, soft modal appears.
  • Image zoom proceeds without waiting for dismissal.
  1. Hard gate save flow
  • Anonymous user at hard limit attempts save -> hard modal appears.
  • After login, pending save is applied once and UI refreshes.
  1. Guest chatbot flow
  • Missing guest quota allows messages; configured quota is enforced by the proxy.
  • Sign-in restores full chatbot access without clearing the guest counter.

D. Manual QA Checklist

Section titled “D. Manual QA Checklist”
  • Mobile Safari OAuth round-trip preserves pending bookmark intent.
  • Desktop Chrome/Firefox/Safari parity.
  • Invalid threshold configuration is reported without imposing an implicit cap.
  • Analytics events emitted with expected names and metadata.

6. Implementation Notes for This Codebase

Section titled “6. Implementation Notes for This Codebase”
  • Keep naming consistent with current code:
    • LoginModal (not ModalLogin).
    • image_clicked and login_modal_showed analytics event naming.
  • Reuse existing auth modal store and user sync hooks where possible.
  • Keep domain-specific thresholds separate; do not restore an implicit FREE_BOOKMARK_LIMIT.
  • A real code paywall requires server-side entitlement enforcement; client counters are only suitable for soft prompts and analytics.

7. Success Metrics and Monitoring

Section titled “7. Success Metrics and Monitoring”

Primary:

  • Social Login Rate.

Secondary:

  • Week 1 retention.
  • Save completion rate after modal exposure.
  • Component preview and export engagement.

Guardrails:

  • Bounce rate on pattern pages.
  • Time on page and image interaction depth.

8. Updated Build Prompt (Copilot/Gemini)

Section titled “8. Updated Build Prompt (Copilot/Gemini)”

“Keep using the existing LoginModal, useAuthModal, Supabase OAuth, and bookmark sync flow. Make product thresholds opt-in, keep visual discovery and component previews open behind only dismissible soft prompts, enforce configured chatbot guest allowances server-side without a period reset, and do not claim paid export enforcement until a real entitlement service exists. Continue emitting login_modal_showed with mode: soft|hard metadata.”
